Boot time is a spread, not a number: the last 10 accepted experiments boot between 12.8 and 15.9 seconds. A single run is not the result.

The question

How small can a NixOS base image for AWS EC2 get while it still boots, deploys, and stays fully usable over SSH?

Not how small an image can be made in principle. How small it can be and still be a machine you would run. The contract fixed that: ten checks, the same script locally and on the real instance, covering the SSH key arriving from instance metadata, DNS, HTTPS with a working trust store, the clock, the root filesystem growing to its volume, and surviving a reboot. A strategy that broke any of them was rejected, whatever it saved.

How it ran

  • One strategy per experiment, measured against a frozen baseline.
  • Two gates: a local QEMU boot, then a real EC2 instance, both running the same contract script.
  • An append-only ledger, one line per experiment, accepted or not.
  • Every removal guarded, so a package that did not actually leave fails the build instead of the review.

The deployment went through nivis, which is the mechanism and not the point. The full method is in the repository.

The descent

Size across all 75 experiments. The flat stretches are the 33 rejections: the line holds while the lab is stuck.

The longest plateau is experiments 20 to 24, where switch-to-configuration was given up on and filed as blocked upstream. Experiment 45 came back to it and took 55 MiB out. A chart of successes only cannot show that.

The one insight

Six strategies account for 795 of the 1 250 MiB, and they are the same finding stated six ways.

A stock NixOS EC2 image carries the tools to rebuild itself. The flake registry, the nixpkgs channel, Python, Perl, the SSM agent, the activation machinery and 57 packages on the system path are all there so the running machine can reconfigure itself. An appliance that is replaced rather than reconfigured needs none of them. Everything after that is smaller and harder: the last 455 MiB took 33 experiments.

Boot time does not track size

One closure, three images, three boots. 604 MB of extra files cost 0.73 seconds.

Boot time fell from 40.8 to about 14.3 seconds over the lab, and none of that is explained by size. The drop at experiment 25 was tested directly and does not reproduce: the image is not what makes the machine slow. The only boot effect ever isolated is compressing the initrd with xz, which costs 2.5 seconds for 4.23 MiB.

The rejections taught the most. Six of them were the lab's own defects, and each one produced a change to the protocol.

  • 4 The guard did its job system.forbiddenDependenciesRegexes is set by each module to name what should have left. It caught #3 (nixos-rebuild still present), #20 and #47 (systemd-minimal had more holders), #52 (elfutils had a third holder) and #57 (krb5 had two more referrers). Writing the guard for what you hope leaves, rather than what you know leaves, is what makes it useful.
  • 6 The lab's own defects Wrong build phase, an unasserted string replacement that silently matched nothing, a measurement that compared only closures, an image that failed to build and was logged as a 100% saving, an integer interpolated into a string, and a mkForce that removed more than it meant to. Each produced a protocol change; see §6.
  • 5 Genuinely too far A trimmed kernel config derails nixpkgs' make config. Dropping the module tree needs ena, af_packet, fuse and configfs force-loaded in the initrd and the firewall off. An auto-sized image with no slack left growpart nothing to grow into.

What belongs upstream

Four results are not about this image. They are things nixpkgs or NixOS does that cost every user, and each one is reproducible from the repository.

  1. Setuid wrappers propagate linuxHeaders into the runtime closure

    nixos/modules/security/wrappers/wrapper.nix takes linuxHeaders as a buildInputs entry; the static stdenv writes nix-support/propagated-build-inputs into the output; the activation script copies the wrapper out of that package, so the file and its 7.20 MiB of kernel headers stay. The binary itself never references them. One postFixup = "rm -rf $out/nix-support" fixes it, and this costs every NixOS system with a setuid wrapper, not just small ones. Ledger #67.

  2. The systemd / linux-pam / util-linux cycle forces a second util-linux

    nixpkgs calls systemd with util-linux = util-linuxMinimal to break it, and NixOS then writes that build into PID 1's PATH and the generator environment, so the image carries two util-linux builds. The lab removed the 8.72 MiB bin output by changing the two PATHs (#65); the remaining 2.47 MiB is referenced by the systemd binary and needs the cycle broken. Overriding the package instead is an infinite recursion, because systemdMinimal resolves systemd from the final package set.

  3. pkgs.bash is bashInteractive

    7.10 MiB against 1.80 for bashNonInteractive, which is already in every closure as runtimeShell. Pointing environment.binsh, users.defaultUserShell, environment.shells, the system path and amazon-ec2-utils at the non-interactive build still leaves two referrers, both hardcoded: stage 2's prepare-root shebang and networking.localCommands. Backlog e28.

  4. make-disk-image's automatic sizing cannot be tuned usefully, and its inode allowance is misleading

    It charges two filesystem blocks per inode; with 13016 files that is 101.7 MiB of a 398 MiB estimate, which reads like the image is mostly slack. It is not: the VHD is sparse, so the estimate only has to be large enough. Halving the allowance moved the allocated size by 64 KiB (#71), and a 1 KiB block size ran the bootloader step out of space (#70). Worth a comment upstream so the next person does not spend three experiments on it. Two further items are blocked rather than upstream-shaped: a compressed store (e3) and any non-ext4 root (e7) both hit make-disk-image's assertion that a partition table implies ext4.

What is next

The reusable result is the measurements, not the image.
